## 三、数据库（44 表）

全表继承 `BaseEntity`：`id`(bigint 雪花)/`create_time`/`create_by`/`update_time`/`update_by`/`is_deleted`/`version`。
唯一例外是 `sys_db_migration`（int 主键 `version`，不继承 BaseEntity）。
软删除全局过滤器**逐实体类型注册**（SqlSugar 泛型过滤器对抽象基类不生效——见踩坑对照）。

| 前缀 | 张数 | 内容 |
|---|---|---|
| `sys_*` | 28 | 认证与会话（user/role/menu/user_role/role_menu/role_dept/position/user_position/dept/user_session）、字典参数（dict_type/dict_data/config）、内容（notice/message）、审计三件套（operation_log/login_log/change_log）、文件（file）、安全（ip_rule）、审批流六表（flow_definition/instance/task/record/cc/binding）、基础设施（db_migration/**doc_seq 单号号段**） |
| `md_*` | 5 | material / supplier / customer / warehouse / price_agreement |
| `scm_*` | 9 | purchase_order(+_line) / sales_order(+_line) / purchase_arrival / stock_doc(+_line) / stock / stock_ledger |
| `biz_*` | 2 | expense / purchase_request（业务样板） |

唯一约束=**过滤索引**（`WHERE is_deleted=false`），现共 **20 个 `uk_*`**，**分散在 8 个迁移文件**里：0001 初始 + 0004/0005/0006 基础资料与供应链 + 0007 库存 + 0011 到货计划 + 0012 单号号段 + 0013 单据表单号兜底——别以为 0001 就是全部。迁移是内嵌资源、由 `sys_db_migration` 记账、幂等、**只前向无回滚**、历史禁改。
⚠️ **「历史禁改」的边界比想象的更严**：记账只认版本号，不认内容。0005 的两条单据索引就栽在这里——它们在**提交之前**就被测试库应用过（那一版还没有这两行），后来补进去就不会重跑，于是「新库有、老库没有」，直到 0013 用 `IF NOT EXISTS` 向前补齐才被目录级不变量用例抓出来。**开发期改迁移文件同样危险**：只要有任何一个库记过那个版本号，改内容对它等于没改；要么新起编号，要么在测试库里 `delete from sys_db_migration where version=N` 让它重跑（仅限自己的测试库）。
**现在这条边界由机器拦着（迁移 0014）**：`sys_db_migration` 多了一列 `checksum`（`varchar(64)`，实体上必须显式写 ColumnDataType，否则给已有表加 string 列会生成 `text(64)` → PG 42601），执行器每次启动比对脚本内容的 SHA-256，**不符就拒绝启动**并指名是哪个文件。哈希前把行尾与尾部空白归一——镜像在 CI（LF）与本机 Windows 构建（CRLF）下拿到的字节不一样，不归一会把老库拦在启动外。加列之前的历史行是 NULL，由执行器第一次遇到时按当前内容补记（一次性豁免，之后不符即拦）。同一个 `Run` 还把「锁外读快照」换成了 `pg_advisory_xact_lock(LockBase+version)` + 锁内复查，多实例同时启动时同一个版本只会应用一次。
⚠️ 这类部分唯一索引当 `ON CONFLICT` 目标时必须把索引谓词再写一遍（`on conflict (col) where is_deleted = false`），否则 PG 直接 42P10。

种子固定小整数 Id（1=admin、20=admin 角色、100 起菜单树）。当前存活菜单 **127** 行（含幂等哨兵 `__seed_v1__` 与按钮级权限行），系统参数 **6** 条。

## 四、核心机制落点速查

| 机制 | 位置 |
|---|---|
| 雪花双通道填充 | `SqlSugarSetup.DataExecuting`（单条）+ `SqlSugarRepository.InsertRangeAsync`/`DbSeeder`（显式） |

| 认证/会话 | `Service/Sys/AuthService`；防爆破 FailCount+LockUntil（阈值=sys_config）；互踢+force-logout；密码有效期 mustChangePassword |
| 防提权四防护 | `UserService`（①重置 admin 拒绝 ②授予 admin 角色仅本人 ③改 admin 角色仅本人 ④停用/删除 admin 拒绝）+ `RoleService.GuardAdminRole` |
| 权限 | `[HasPermission]`→`perm:` 动态策略（`Api/Authorization`）+ `PermissionService`（版本整体失效）；数据权限 `DataScopeService` 五档表达式（预解析常量，红线 #1 合规） |
| 审批引擎 | `Service/Sys/FlowEngineService`（九大语义）+ `ConditionEvaluator`/`FlowGraphValidator`；回调 `IFlowBusinessHandler` 按 BusinessTable（AddScoped 多实现） |
| 审计三件套 | 操作日志 `OperationLogFilter`（ActionArguments+词根脱敏）；登录日志 AuthService；变更日志见上 |
| 内置作业 | `Api/Jobs/SystemJobs.cs`：sys.log.cleanup(0 2)/sys.backup.daily(0 3, pg_dump -Fc + uploads 镜像 + 保留期, 失败站内信)/sys.notice.publish(* * * * *)；`JobManagementService` 支撑监控页 |
| 安全 | 密码 PBKDF2-SHA256(10 万次/16B 盐) + legacy 哈希透明升级；强度策略 ≥8 位含 3 类；有效期 `sys.pwd.expireDays`(90) 超期强制改密；上传白名单+大小+魔数；JWT 密钥启动校验 ≥32 字符；登录/验证码限流（RateLimit:LoginPermit 可配）；IP 黑白名单（CIDR，白名单豁免限流）；**强制改密的门在服务端**（`OnTokenValidated` 每条请求判一次，只放行改密/看资料/刷新/登出四条端点） |
| 并发一致性 | 单号＝`sys_doc_seq` 号段 + `UPDATE…RETURNING` 原子取号（`DocNumbers`），并且**五张单据表都有 `uk_<表>_doc_no`（`WHERE is_deleted = false`）做数据库兜底**——0013 之前 biz 两张一直裸着；`DocNoUniqueTests` 用目录级不变量钉住这件事（新增单据表忘了建索引会当场红）。库存过账＝一条 `UPSERT…RETURNING`，`quantity+delta>=0` 由数据库判；单据状态流转＝`UPDATE…WHERE status=@期望 RETURNING version`，0 行即 409（`StockDocService.ClaimStatusAsync`）。⚠️ 三处都**不许退回「先读出来判一下再按主键写」**，`ConcurrencyTests` 四条用例钉着 |
| 防重复提交 | `[NoRepeatSubmit]`（用户+方法+路径+参数哈希，默认 2s 窗）已挂在 11 个「点一次做一个动作」的端点：过账/作废/各类提交审批/审批动作。⚠️ 它是 get-then-set 的**尽力层**（非原子，且只在单实例内存里），真防线是上面那条数据库守卫；`create` 刻意不挂——连续录两张内容相同的单是正常操作 |
| 探针 | `/api/v1/health` 存活（不查依赖，容器 HEALTHCHECK 打它）；`/api/v1/health/ready` 就绪（`select 1`，3 秒超时）。⚠️ 有 SPA 兜底，判端点存在要核响应体不是状态码 |
| 可观测性 | **关联 ID**：`CorrelationIdMiddleware` 是管道第一站（在 Serilog 请求日志与异常中间件之前），沿用调用方带来的 `X-Correlation-Id`——只接受 8–64 位 `[A-Za-z0-9._-]`，脏值一律重新发号（它会进日志、也会回显到响应头）；同时写响应头 + Serilog `LogContext`，日志模板带 `[{CorrelationId}]`，异常日志记这个号而非 `TraceIdentifier`。**指标**：`RequestMetrics`（Interlocked 计数）→ `GET /api/v1/monitor/metrics`，给**自启动累计量**（状态码分布、平均/最大耗时、GC 分代与停顿占比、线程池占用、`pg_stat_activity` 连接数）。刻意不做百分位、不引 Prometheus 依赖：要速率就按固定间隔抓两次算差值 |
| 前端底座 | **动态路由**：登录后按 `sys/menu/tree/my` 注册路由，没授权的菜单不注册，直接敲 URL 由守卫弹 `/403`（`router/index.ts`）。**多页签**：`stores/tabs.ts` + `keep-alive`。**令牌单飞刷新**：`api/http.ts` 用一个共享的 `refreshing` Promise，并发 401 只发一次 refresh、其余请求排队等它（`refreshing ??= doRefresh().finally(清空)`）。**亮暗主题**：`components/AppProviders.vue` 按 `isDark` 切 `darkTheme` 与 `styles/theme.ts` 两套 overrides。**实时**：见上一节 SignalR 行。首页仪表盘刻意只放业务量（待办/未读/公告/可用功能），不写这些实现名词 |

## 九、多副本扩容前置（当前形态 = 单副本）

`docker-compose.yml` 只起一个 `panshi-api`，代码里的若干机制**按单副本写的**。下面每条都给 file:line，是要上多副本时的施工清单；没打勾之前，请把「横向扩副本」当作不支持项，而不是「反正微服务都能扩」。

### 必须先解决（不解决就是安全事故，不是性能问题）

1. **进程内缓存 = 权限与黑名单的一致性**：`Program.cs:109` 把 `ICacheService` 注册成 `MemoryCacheService`（`Panshi.Common/Cache/ICacheService.cs:23` 默认 TTL **30 分钟**）。两个受害者靠**进程内静态版本号**失效，跨副本不传播：
   - `Service/Sys/PermissionService.cs:27` `InvalidateAll()` 只是 `Interlocked.Increment(ref _version)`，缓存键 `perm:auth:{userId}:{_version}`（同文件 31 行）。**A 副本改了授权，B 副本最长 30 分钟仍按旧权限放行**——收回权限不生效，属于安全问题。
   - `Service/Sys/IpGuardService.cs:36` 同款版本号（写操作后 150/171/177 行 `InvalidateAll()`）：**新加的封禁在别的副本最长 30 分钟不生效**。
   - 顺带：`Api/Filters/NoRepeatSubmitFilter.cs:15` 也走这个内存缓存，双击落到不同副本就挡不住（它本来就是「尽力层」，真防线是数据库守卫，见 §四「防重复提交」行）。
   → 出路：`ICacheService` 换 Redis，或把版本号搬到 DB/Redis 做广播；不做就得 LB sticky + 手工刷缓存，都属于脆弱方案。
2. **验证码是进程内的**：`Program.cs:104 AddCaptcha(...)` 用 Lazy.Captcha 默认存储（`X-Captcha-Id` → 答案）。A 副本发图、请求落到 B 副本 → 永远「验证码错误」，登录整站不可用。→ 出路：分布式存储，或换一种跨副本成立的登录校验。

### 要知道的性质（不修也能跑，但表现和单副本不一样）

3. **雪花机器号必须互不相同**：`appsettings.json:32 Db:SnowflakeWorkerId=1` → `Program.cs:192` → `Repository/SnowflakeId.cs:20`（位宽 6，合法 0–63）。同 workerId 同毫秒可发出相同 id，届时主键与 `uk_*_doc_no` 会拒（业务侧报 500，不是静默脏数据，但很难看）。注入点已存在，只是 compose 没区分副本：给每副本设 `Db__SnowflakeWorkerId=1..63`（互不相同）即可；讲究一点可以做「启动时向 DB 申领 worker id」。
4. **限流按副本各算各的**：`Program.cs:65-75` 是 `GetFixedWindowLimiter`（按客户端 IP 分区，进程内计数），`RateLimit:LoginPermit=10/分钟`、`CaptchaPermit=60/分钟` 在 N 副本下实际约 N 倍。别把限流当全站保险——**防爆破不在这条路上**：`fail_count`/`lock_until` 写在 `sys_user`（DB），跨副本天然一致。
5. **SignalR 没有 backplane**：`Program.cs:60 AddSignalR()` 未接 Redis。用户连在 A 副本、消息由 B 副本产生 → 这次实时推送收不到（**数据不丢**：站内信仍在库里，下次拉取/刷新列表就看得到）。→ 出路：`.AddStackExchangeRedis(...)`。
6. **落盘目录是容器本地的**：上传走 `Api/Services/FileStorage.cs:14-15`（`Db:UploadDir`，compose 挂 `./data/uploads:/app/uploads`），备份走 `Db:BackupDir=/backups`（compose `docker-compose.yml:36`，挂 `./backups`）。**同一台主机**上多副本共享同一目录还行；**跨主机**就成了两份互不相干的目录——上传的文件在另一个副本下载不到、备份散在两处。→ 出路：NFS/对象存储，或把上传与备份收敛到单实例（拿锁竞争的那个副本之外不写盘）。
7. **指标只反映被访问的那个副本**：`Api/Middleware/RequestMetrics.cs` 是 Interlocked 进程内累计，`GET /api/v1/monitor/metrics` 不代表全站。要做全站指标得汇聚（每副本暴露 + 采集端求和），别把单副本数字当集群结论。

### 明确不受副本影响（别误当坑去改）

- **迁移**：`Repository/DbMigrationRunner.cs` 现在是「`pg_advisory_xact_lock(LockBase+version)` + 锁内复查 + 内容指纹」（迁移 0014），多副本同时启动也只会应用一次，改过的历史脚本会被硬拦。
- **内置作业的调度**：`Program.cs:197-198` 用 PG 存储的 Hangfire，RecurringJob 的下次触发时间存在库里，同一时刻**只入队一次**、由任一 server 执行——不会重复跑。⚠️ 我此前把「Hangfire 多副本会重复跑」列为坑，是错的；真正的多副本问题是第 6 条的落盘位置。
- **会话/令牌/强制改密门**：`sys_user_session` 与 `OnTokenValidated` 里的判定都读 DB，跨副本一致。
- **单据状态机、库存过账、发号**：三条数据库级原子守卫（§四「并发一致性」行）本就来自多写者场景，副本数无关。

**当前决定**：按单副本部署（一个 api + 一个 db，主机 18080）。要真上多副本，第 1、2 条是前置项，第 3–7 条是要一并调整的配置与预期。
